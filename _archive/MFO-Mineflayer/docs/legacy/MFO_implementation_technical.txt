# Minecraft Farm Observatory (MFO)

## Technical Architecture Specification v1.0

---

# 1. Project Overview

## Purpose

Minecraft Farm Observatory (MFO) is a **read-only observability platform** for technical Fabric servers.

It is **not** an automation mod.

Its purpose is identical to infrastructure observability tools (Prometheus, Grafana, ELK):

* Observe
* Collect metrics
* Store historical data
* Detect anomalies
* Alert operators
* Visualize system state

Gameplay is never modified.

---

# 2. Design Principles

## Read Only

The manager must never modify world state.

Allowed actions:

* teleport
* rotate camera
* open inventories
* inspect inventories
* inspect entities
* inspect blocks
* read chunks
* capture screenshots
* receive packets

Forbidden actions:

* block breaking
* placing blocks
* dropping items
* moving items
* clicking inventory slots
* crafting
* attacking
* eating
* trading
* activating blocks

Any feature violating this principle is out of scope.

---

## Configuration Driven

Nothing is hardcoded.

Everything is defined by configuration.

Examples

* farms
* storage
* cameras
* alerts
* dashboard
* discord
* workers

---

## Event Driven

Subsystems never directly call each other.

Everything communicates through an Event Bus.

Example

```
StorageScanner

↓

ContainerScanned Event

↓

Metrics Service

↓

Health Service

↓

Alert Service

↓

Discord
```

No service knows who consumes its events.

---

## Plugin Based

Every monitor is independently pluggable.

Example

```
StorageMonitor

EntityMonitor

ChunkMonitor

WorkerMonitor

VillagerMonitor

ProductionMonitor

ScreenshotMonitor
```

Each implements a common interface.

# 21. Coding Standards

* Enable `strict`, `noUncheckedIndexedAccess`, and `exactOptionalPropertyTypes` in TypeScript.
* Use dependency injection for services; avoid global singletons except the application bootstrap.
* Separate domain models from persistence models (don't expose ORM entities directly).
* All configuration should be validated at startup with descriptive errors.
* Every asynchronous task should support cancellation (e.g., `AbortSignal`) so the scheduler can interrupt or reprioritize work.
* Use structured logging with correlation IDs (e.g., one ID per scheduled job) to trace operations across components.
* Design monitors to be idempotent: rerunning a scan should not produce side effects beyond duplicate observations.

# 22. Future Extensibility

The system should support additional monitor plugins without changes to the scheduler or core event bus. Examples include:

* Villager population and workstation validation
* Beacon status monitoring
* Redstone power state sampling
* Mob-cap monitoring
* Hopper throughput analysis
* Dimension-level statistics
* Server TPS and MSPT integration
* Prometheus metrics exporter

The core should remain stable while new observability modules are added as independent plugins implementing the common monitor interface. This keeps the project maintainable and scalable as the technical server evolves.
