This is a solid design. The biggest strength is that you're treating this as **observability infrastructure**, not gameplay automation. That keeps the scope focused, avoids feature creep, and makes it easier to maintain.

Below is the architecture specification I would give to Claude Code.

# Minecraft Farm Observatory (MFO)

## Goal

Minecraft Farm Observatory (MFO) is an observability platform for a Fabric technical Minecraft server.

It **does not automate gameplay**.

It only observes the server, gathers metrics, takes screenshots, computes health, and alerts players.

Think of it as:

> Prometheus + Grafana + CCTV for Minecraft farms.

---

# Core Principles

## Read-only

The Manager may:

* Teleport
* Open containers
* Read inventories
* Rotate camera
* Capture screenshots
* Stream camera
* Read entities
* Read blocks
* Read dimensions
* Read chunk state

The Manager may NEVER:

* Move items
* Pick up items
* Drop items
* Place blocks
* Break blocks
* Attack
* Trade
* Craft
* Press buttons
* Flip levers
* Activate redstone

The only gameplay permission is teleportation.

# Components

## Mineflayer Manager

Singleton.

Only one instance exists.

Responsibilities

* Teleport
* Scan farms
* Capture screenshots
* Open inventories
* Calculate storage
* Observe entities
* Report metrics

Stateless.

Never permanently assigned to a farm.

---

## Carpet Workers

One per farm.

Responsibilities

* Load chunks
* Keep farms operational
* Execute repetitive Carpet actions

Workers never communicate.

The Manager observes them.

---

Configuration-driven.

Example:

```yaml
farms:

  iron:

    dimension: overworld

    teleport:

      x: 120
      y: 80
      z: -500

      - type: chest
        position: [123,79,-501]

      - type: barrel
        position: [124,79,-501]

    cameras:

      overview:
        yaw: 180
        pitch: -20

      storage:
        yaw: 90
        pitch: -35

```

No hardcoded farms.

# Event Bus (Internal)

Everything communicates through events rather than direct calls.

Examples:

```text
ContainerScanned
ProductionUpdated
HealthComputed
AlertTriggered
ScreenshotCaptured
WorkerMissing
ManagerConnected
UnknownPlayerDetected
```

This keeps the system modular and makes it easy to add new monitoring features.

# Future Plugin System

Design every scanner as a plugin implementing a common interface:

```ts
interface FarmMonitor {
  id: string;
  scan(farm: FarmContext): Promise<ScanResult>;
}
```

Built-in monitors could include:

* StorageMonitor
* ProductionMonitor
* WorkerMonitor
* ChunkMonitor
* EntityMonitor
* CameraMonitor

This allows adding new observability features (e.g., villager health, beacon status, redstone state, hopper throughput, mob counts) without modifying the core scheduler or health engine.

## Development Roadmap

I would implement the project in these phases:

1. **Foundation**: configuration loading, event bus, scheduler, database, logging, and Mineflayer connection.
2. **Observation**: teleportation, storage scanning, screenshots, camera presets, and entity scanning.
3. **Health & Metrics**: production calculations, farm health computation, historical storage snapshots, and alerts.
4. **Integrations**: Discord commands/notifications, REST API, WebSocket events, and Prismarine Viewer.
5. **Dashboard**: live overview, farm pages, charts, alert management, authentication, and screenshot gallery.
6. **Polish**: plugin system, configuration validation, backups, testing, documentation, and Docker deployment.

This architecture is intentionally modular: every subsystem communicates through events, every farm is configuration-driven, and the Mineflayer Manager remains a **read-only observer** while Carpet workers remain **simple infrastructure actors**. That separation should keep the system maintainable even as your technical server and number of farms grow substantially.
